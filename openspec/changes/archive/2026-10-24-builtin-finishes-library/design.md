# Design

## Context

Room surfaces already draw project library materials (`library-material.ts`, `library-uv.ts`, `geometry/library-surface.ts`), with maps fetched by a per-document `TextureSource` that exists only when a project manifest is loaded. The bundled finishes go through the legacy path (`finishes.ts` and the canvas generators). The Basis transcoder already ships beside the player file and is found through `shared/own-url.ts`.

## Decisions

1. **Folder.** `finish-maps/` at the repository root, tracked:
   1.1 `tex/<versionId>/<role>.<px>.webp`, at 256, 512 and 768, with the same set for every role.
   1.2 `index.json`: `format: 1`, `finishes[]` (finish id, then either library variant id, version id, optional tint `colour` and `rotation`, or `kept: true` for a finish whose material is not chosen yet), and `versions[]` (version id, kind, facts, maps by role, and every file's path, bytes and SHA-256, plus source facts).
   1.3 `SOURCES.md`: one row per scan with provider, source page, licence and the transformations applied.
   The ids are opaque UUIDs chosen by the library. The player never mints or composes one; paths are derived from the version id, role and size, which composes a path and not an id.
2. **Runtime table** `src/materials/builtin-library.ts` is generated by the authoring script and checked by a test against `index.json`. Its compact records are expanded by a pure helper into `LibraryMaterial` values, with no hashes and no provenance. Only `room-finish.ts`, `shell-paint.ts` and the UI import it, so the imports of `finish-catalogue.ts` and the `ops` entry stay unchanged. The rows of `finish-catalogue.ts` keep their ids, names and order; only the `base` literal of a bound row changes, to the library first-frame colour, and a test pins that equality. The table has two parts: `finishes` (bound room finish ids) and `defaults.ceiling` (the default ceiling draw).
3. **Kept finishes.** A finish marked kept has no table record and resolves through the legacy lookup exactly as before (generated texture, swatch and preset chip). A later re-fetch binds it without code changes.
4. **Resolution.** `resolveRoomFinish` returns a project material (any kind) first, then a built-in library draw flagged `builtin` for a BOUND room finish id, then the legacy lookup. The default-ceiling id belongs to the object bank: it is never in `finishes`, so `resolveRoomFinish` never answers it from the table, it never becomes a picker option, the validator's accepted ids do not change, and furniture finishes keep their generators.
5. **Sources.** `BuilderContext` carries `builtinTextures` next to `textures`, as an optional trailing parameter of `createBuilderContext` defaulting to `null` (so the light-bake callers stay untouched), through `SceneBuilderOptions` and the context `rebuildAll` recreates. `ShellPaint` loads a built-in draw from `builtinTextures`. `LibrarySurface` remembers the source it acquired from and releases to it. `SceneMount` owns one built-in `LibraryTextures` per viewer, with `attached` invalidating the render demand. It is created on the first mount that has a texture environment, its base is `transcoderFolder(OWN_FILE_URL)` (which falls back to `document.baseURI`) plus `finish-maps/`, and it takes no host resolver and a logger adapter that lets the first warning through and drops the rest. Its `start()` (idempotent) is scheduled a frame after EVERY mount, so a mount released before its first frame cannot leave it deferred; it is kept across `release`, `remount` and document swaps, and disposed by `SceneMount.dispose`.
6. **Ceiling.** `ShellPaint.registerCeiling` replaces the builder's flat fallback with one shared library material per paint instance: the project's library material under the default ceiling id when `ctx.resolve` gives one, else `defaults.ceiling` of the table. A per-room repaint never releases that material; `releaseLibrary` does. When the table has no default ceiling (kept), the builder's flat fallback stays.
7. **Bypasses.**
   7.1 The floor fallback resolves `DEFAULT_FLOOR_FINISH` through `ctx.resolve`.
   7.2 `paintWall` paints a bound built-in id flat in its first-frame colour, which covers the junction cores the builder paints in place.
   7.3 Preset chips use their flat pair when either finish is bound.
   7.4 Bound picker swatches use the shipped 256 albedo URL for natural scans and the flat colour otherwise.
   7.5 A bundled option is dropped when a project option with the same id is listed.
8. **Build plugin** `scripts/finish-maps-plugin.ts`, used by `vite.config.ts` (prefix `assets/`), the `es` and `iife` passes of `vite.lib.config.ts` and `vitest.config.ts`:
   8.1 It reads `finish-maps/index.json` at config time.
   8.2 It emits every indexed file and `SOURCES.md` under `<prefix>finish-maps/`.
   8.3 In development it answers GET and HEAD for paths ending in `/finish-maps/tex/<uuid>/<role>.<px>.webp` with the indexed file only, and 404 for any other path under that suffix.
9. **Authoring script** `scripts/finish-maps-fetch.ts --map <file> --store <url> [--update]`, with the key from `STORE_DEV_KEY`:
   9.1 It reads the mapping rows, with the pinned version facts per row; a row marked `keep` or `pending` becomes a kept finish. Roles follow the store's projection: `albedo` or `albedoTint` by colour mode, `normal` unless its strength is 0, and `arm`.
   9.2 For every role and size it asks the store's map endpoint for a signed URL and downloads the bytes.
   9.3 It checks the WebP signature, the pixel size, the per-file cap and a hash already recorded under the same path.
   9.4 It writes into a staging folder, then swaps it in, rewrites `index.json` and `SOURCES.md` and regenerates `builtin-library.ts`.
   9.5 A version change against the current index needs `--update` and is printed.
   The key is never written.
10. **Distribution.** The folder ships like the Basis transcoder: emitted beside the player files in the demo build (and so on the player site) and in `dist-lib`, found next to the running player file, with no viewer option to name another place. It is left out of the npm package (`"!dist-lib/finish-maps"` in `files`). The README names the copy step: take `finish-maps/` from the repository (or the built `dist-lib/finish-maps/`) and place it next to the player file a host serves, so `<player folder>/finish-maps/tex/...` resolves. Without the folder the surfaces stay flat in their library colour with one warning.
11. **Budget.** `scripts/budget-check.ts` gains a check of the folder: the total bytes under a measured limit plus 5 %, every file under `MAX_TEXTURE_FILE_BYTES`, and the largest single-size set (every scan at 768) under `MAX_PROJECT_TEXTURE_BYTES`, the budget the viewer-lifetime source never resets. The boot growth of the table is measured with the gate's gzip and recorded.
12. **Export.** It is unchanged in code. Without a texture source, built-in surfaces export in their first-frame colour. The path stays a single one, so a later textured export only needs a source.

## Risks

1. Size. Measured on a store scan: about 1.4 MB per scan for all three sizes (the lossless ARM at 768 is 628 KB), so about 1.4 MB times the bound scans in the repository, the site and `dist-lib`. A visitor downloads about 85 KB (low), 375 KB (mid) or 957 KB (high) per scan shown.
2. GPU memory. Three RGBA8 maps at 768 with mipmaps are about 9 MiB per resident scan; a scene rarely shows more than five scans at once.
3. An npm consumer, and a host that re-bundles the ES entry, must copy the folder. The README says so; without it the surfaces stay flat with one warning.
4. Maps arrive after walk lighting has sampled the room. The first-frame colour is the map average, so the bounce barely changes.
5. Bakes made before this change of a bare scene were made with the old albedo; `shellInputsHash` does not change, so they stay eligible and must be re-baked. `src/lightmap` stays untouched.
