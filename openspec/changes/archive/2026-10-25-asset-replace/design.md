# Design

## Context

The Replace panel lists `variantsForPlacement` of the selected placement (`asset-variants.ts`), looked up through a `VariantBank` (the project's catalogue) with the bundled bank behind it. The only swap op, `replace_asset_variant`, refuses a variant of another archetype. `place_object` needs a new id. The asset resolver accepts a placement's `library` only when it is the document's own or the one injected catalogue library (`asset-resolver.ts`). The validator reads `CATALOGUE_REGISTRIES`, nested by `registriesFromLibrary` for a project. Panels are vanilla DOM in the viewer shell (`selection-panel.ts`) with a root-aware focus trap. Native modal dialogs are avoided because inertness does not stop at a shadow root.

## Goals / Non-Goals

Goals: every variant reachable; a cross-asset replacement that keeps the placement id; a host-supplied catalogue in the existing library format; keyboard and phone use.

Non-goals: building the catalogue (jeex-studio does); prices and access rules (carried, never judged); localised category names; replacing openings; replacing across anchors.

## Decisions

1. **The op.** `replace_asset` lives beside `replace_asset_variant` in `scene/ops/assets.ts`, with its type in `scene/types.ts`, its schema in `types.schema.ts`, and a dispatcher case. Through the `registries` parameter, it resolves the target as `library ?? scene.assetLibrary ?? bundled`. It compares `anchor` and `onSurface === true` with the current archetype (`CatalogueArchetype`, the public registries input that hosts build, and `projectLibraryOf` gain `onSurface`), checks the mirror against the target's `MirrorFacts` with the existing mirror check, then rewrites the placement as the spec says and calls `forgetInPresets` for that placement's variant ops and finish-setting `set_object` ops. Position is copied, never reseated.
2. **Scene diff.** `scene-diff.ts` treats a change of `library` the way it already treats a change of `asset`: as a new body.
3. **Offers loading.** `ViewerOptions.offers?: { url: string } | { library: ProjectLibraryManifest; baseUrl: string }`. The `offers` attribute maps to `offers.url` in the option schema; the inline form is opaque for the deep merge and in `schema/viewer-options.json`, like `scene.library`. `assets/offers.ts` fetches the URL (no credentials, the existing JSON size cap), parses it with the library schema (now exported as `parseProjectLibrary`) and derives `baseUrl` from the URL. `loadDocument` awaits it BEFORE validation: a mount with URL offers waits for them, and the offers identity joins `LoadedProjectContext.key` so a model judged without them is never reused. Offers are validated by the standalone library schema only; the project-manifest rule tying a library id to the project id does not apply, because offers carry their own UUID. A failure, or an offers id equal to the project library's, logs `offers-invalid`, and the mount goes on without offers. The inline form stays `{ library, baseUrl }`, not `{ manifest, baseUrl }`: offers are a library, not a baked project.
4. **One layered bank.** A small `assets/library-stack.ts` composes the project bank, the offers bank and the bundled bank. It is built whenever there is a project or offers, bare scenes included. It answers a `CatalogueLookup` whose `CatalogueMatch` carries the owning library id and folder, and an ordered `entries(libraryId)` for listing. The asset resolver takes the list of accepted libraries instead of one `catalogueLibrary`, and model and preview URLs resolve against the owning folder. Materials, finish resolution, textures and asset facts are layered in the same order. The validator nests `registriesFromLibrary(project, registriesFromLibrary(offers, CATALOGUE_REGISTRIES))`. The light bake's `BakeBank` takes the stack. `jeex-viewer/ops` exports `parseProjectLibrary` and `libraryOf` (a bare library to the registries input), so a host validates the same way.
5. **Panel reachability.** `.finish-panel` gets `max-block-size` bounded by the viewer, and only `.finish-swatches` scrolls (`overflow-y: auto`, `overscroll-behavior: contain`). The furniture panel is anchored at the top (y 64), so `anchor()` sets `max-block-size` to the viewer height minus the top and a margin; nothing is measured.
6. **The button.** `PanelRequest` gains an optional second footer action, rendered under the existing one in a new row with its own shell name in `viewer-shell.ts` (covered by the CSS contract check), so no existing control moves. The furniture request sets it when the editor allows edits.
7. **The popup.** `ui/replace-popup.ts` is a viewer-local modal: a backdrop inside the shell, a titled region (`role="dialog"`, `aria-modal`, `aria-labelledby`), the root-aware focus trap the panel already uses, Escape and a close button, and focus returned to the opener. The list is built by a pure `replaceOffers(placement, stack)` over `offers`, else the bundled bank (never the project library): same anchor pair, a mirror the target allows, the current archetype excluded, grouped by the top segment of `category` in first-seen order (one group per leaf left a column of one-card groups, and card names already say "Dining table"), each group labelled by that segment with dashes and underscores turned into spaces and the first letter capitalised. Thumbnails use the declared preview, else a rendered preview of the archetype's default variant made by the same `renderPreview` the Replace panel uses (cached per archetype), else the palette chip. The bundled bank declares no previews, and the player site and playground offer it alone until a host serves offers, so the bundled popup must look finished on its own. A narrow viewer gets a full-width sheet.
8. **Commit.** A pick always names the variant: the offered archetype's default variant as listed when the popup opened, never left to whatever the default is at commit. A pick calls the editor's dispatch with `replace_asset`, so `local` and `emit` behave as for variants. In local mode, the bundled fallback commits directly. An offers pick sets `library` to the offers id.

## Risks / Trade-offs

- A replacement with a different footprint may overlap its neighbours or lose its on-surface host. The layout linter reports this as it does after a move. The op does not refuse it.
- A legacy type alias carries yaw compensation, so a replaced alias placement may face differently. Bundled demo scenes name UUIDs, so this rarely shows.
- Offers fetched by URL delay the mount by one request. Hot-swapping registries after mount was rejected: the model keeps the registries it was built with.
- A stored document that names the offers library opens only where the same offers are supplied. jeex-studio supplies them and validates with `libraryOf(parseProjectLibrary(...))`.
