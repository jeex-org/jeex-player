# Design

## Context

Bundled room finishes are rows of `finish-catalogue.ts` (ids in `finish-ids.ts`); a row bound by the generated table (`builtin-library-data.ts`, expanded by `builtin-library.ts`) is drawn as a library material through `resolveRoomFinish`. The table and `finish-maps/` are written by `scripts/finish-maps-fetch.ts` from the library's room-finish mapping. The catalogue module must not import the table (the scene-operation entry stays map-free). See proposal.md for the motivation.

## Goals / Non-Goals

Goals: the approved set drawn under stable ids, three aliases that resolve on read and never rewrite a document, the script and the shipped folder brought to the mapping.

Non-goals: a herringbone generator, coat normal maps, changes to lighting or post-processing, a change to the light-bake input hash contract.

## Decisions

1. **Alias records in the pure catalogue.** `finish-catalogue.ts` holds `RETIRED_FINISHES`: alias id, historical slug, target id; the public `FINISH_ALIASES` (decision 11) is derived from it. The catalogue index points an alias id at the TARGET's own `Finish` object and family (never a copy), so `findFinish`, `finishKind`, validation, completeness and preset chips answer for it. The picker lists (`FLOOR_FINISHES`, `WALL_FINISHES`) drop the three alias rows. One pure helper, `bundledAliasTarget(id)`, answers the target or `undefined`. `findFinish(alias).id` is the target's id: it is a lookup answer and is never written back into a document (no current caller does). Rejected: aliases only in the generated table (catalogue and rendering would disagree), a parse-time map (a second resolution system).
2. **Resolution order** in `resolveRoomFinish`: a project material under the authored id (alias id included) wins, any kind; else the bundled binding of `bundledAliasTarget(id) ?? id`; else the legacy lookup. The draw keeps the AUTHORED id as `id` (material and export names keep the alias spelling); maps are cached per library version, so an alias fetches nothing extra. A project material under the target id does not override an alias: the alias reads the bundled target.
3. **Picker.** `finishCore` keeps two values: the stored reference (`finishCurrentOf`) and the shown one. The shown current is the alias target when the stored id is a bundled alias and the project ships no material under the alias id; the options never include an alias. The public `describeSelection(...).current` is that shown id (a documented behaviour change for hosts); the stored reference stays visible in `scope.ops`. Scope operations are built from the stored reference, so "apply to all" spreads the alias. In the built-in panel, the footer applies the stored reference while the active swatch is still the shown current and no swatch has been picked; after a pick it applies the active swatch, as today. A swatch pick writes the picked id.
4. **Slug table.** `CATALOGUE_ID_BY_SLUG.finish` keeps `ash`, `wallpaper-cream` and `wallpaper-sage` mapped to the alias ids.
5. **New rows.** Ids are literals copied from the mapping into `FINISH` (never minted or composed). Floors: `herringbone`, `herringbone_dark` (`planks`). Walls: `pure_white`, `ink`, `venetian`, `microcement`, `microcement_grey` (`plaster`), `travertine`, `marble` (`tiles`, stone), `porcelain_grey`, `zellige` (`tiles`, ceramic). New rows follow the existing ones in their list. `base` of every bound row equals its library first-frame colour (existing test); `name` equals the mapping's name (new test through `index.json`). `kind`, `tile` and the other legacy fields only matter if the table were absent; the scan's own tile and grain draw the surface.
6. **Index and table.** An index entry gains an optional `name`, and a third shape `{ finish, slug, alias }`. The generated table holds bindings only; aliases live in the catalogue, and a test holds `RETIRED_FINISHES` equal to the index's alias entries.
7. **Authoring script.**
   7.1 Mapping rows accept `alias: <uuid>`; exactly one of `material`, `keep`, `pending`, `alias` per row.
   7.2 Before fetching: finish ids unique across rows; an alias target is another row's finish, bound or kept, not itself, not an alias.
   7.3 Two rows naming one version must give identical facts.
   7.4 Any change of an existing entry's binding state against the previous index (version, tint, rotation, bound to alias, kept to alias, alias target, or the entry dropped) is a change that needs `--update` and is printed; new finish ids are additions.
   7.5 Bytes under an already recorded path must not change, with or without `--update`; caps are never waived.
8. **Clear coat.** `PHYSICAL_FIELDS` already lists `clearcoat` and `clearcoatRoughness`; a test pins that the zellige binding becomes a `MeshPhysicalMaterial` with the mapping's values and that a GLB export writes them.
9. **Demo presets.** Floors on Bleached ash move to Herringbone oak, walls on Cream stripes to Warm white, walls on Sage stripes to Olive limewash. Preset names: "Chalk and herringbone", "Walnut and terracotta", "Sage and mocha" ("Oak and sand" unchanged). Fixtures that model saved documents keep the alias ids.
10. **Bake hash.** `shellInputsHash` hashes the scene and its named project materials, not bundled finish data: it does not change (an existing literal test pins it). A bake made earlier of a scene on a changed finish keeps its hash and must be made again.
11. **Public alias table (public API addition).** `jeex-viewer/ops`, the entry an editor host already reads the finish slug table from, exports `FINISH_ALIASES`: a frozen, null-prototype record of alias id to target id, derived from the catalogue's alias records (one source). It is documented in the entry's header and pinned by the entry's export-list test and a test that it equals the catalogue's records. Beside it, `FINISH_NAMES`: a frozen, null-prototype record of every bundled room finish id (floors and walls) to the name the picker shows; aliases are left out (a host resolves them through `FINISH_ALIASES` first), and the object bank is not included. A host's picker reads both instead of copying ids or naming finishes by slug; The `ops` entry also carries the eleven new id literals and catalogue rows (random hex gzip cannot fold), likely about 1 KB in all: `build:lib` re-measures it and `OPS_BUDGET_FAIL_BYTES` becomes the measured size plus 1 KB with its comment updated, the rule that budget already states. The texture caps of decision 12 are a different kind of limit and are never raised. README (ops section) and CHANGELOG name the export.
12. **Budget.** `FINISH_MAPS_BUDGET_BYTES` = the emitted folder (maps plus `SOURCES.md`) measured after the re-fetch, plus 5 %. The per-file cap and the all-at-768 cap (`MAX_PROJECT_TEXTURE_BYTES`) are unchanged; if either fails, the work stops.

13. **Window and door frames.** Four opening variants drew their frames (and two their leaves) in the graphite room paint, which becomes Mocha, a warm brown. They take their own finish instead: `FINISH.frame_graphite` ("Graphite powder coat"), a code constant minted once offline beside the other finish literals, drawn as the library's powder-coated metal (Metal 027) tinted `#6a6862`, the old graphite grey. It is drawn flat through `createLibraryMaterial`, with its version facts pinned in `materials/frame-finishes.ts` and no maps fetched: frame parts are boxes whose UVs run 0..1 per face, not the world-metre UVs a scan's tile is laid out on, so maps would stretch over every face. The light-bake shell contract records the new id for those frame and leaf meshes; nothing else in the contract changes (no input, hash or schema field).
14. **Order of work.** The data comes first: the script learns alias rows (red, code), then the red integrity and catalogue tests, then ONE code commit with the re-fetched folder, the regenerated table and the catalogue rows (they only agree together). Resolution, picker, ops export and demo follow as their own pairs.

15. **Rectangular maps** (found while re-fetching). The library renders the map of a rectangular tile (the porcelains and microcements, 3.6 by 1.8 m and 1.1 by 0.55 m) at the named size on its longer side, so 256 is 256 by 128. The player required square images. The WebP decode check now accepts a longer side equal to the named size and a shorter side equal to that size over a power of two; UVs already divide by `tileM` per axis, so one image covers one tile. The authoring script refuses, before any fetch, a tile whose sides are not in a power-of-two ratio, and checks that every image has the tile's shape. KTX2 containers stay square (no rectangular KTX2 is shipped).

16. **Identical maps under two versions** (found by the full gate). The library ships some scans under two versions with byte-identical maps (the facade's Oat limewash and the default ceiling's lime plaster, the porcelains, the microcements, the two whites). The export now tells images apart by their pixels, so such a map is written once; a compressed texture stays keyed by its source.

## Risks / Trade-offs

1. [Folder size about doubles] → only on-screen finishes are fetched, at the device's size; the budget is re-measured.
2. [Herringbone scans declare `grain: unknown`, so they are not turned to a room's long edge] → accepted; the scan draws as authored.
3. [Clear coat sits on the unperturbed normal in three.js] → accepted; no coat normal map in this change.
4. [Older bakes of scenes on changed finishes still match their hash] → named in the release notes; re-bake.
5. [A project override of a target does not reach its aliases] → documented precedence; a project that wants it ships a material under the alias id too. Its option may still be marked current on an alias wall that draws the bundled target: vanishingly unlikely, not built for.
6. [Pixel-reading browser tests on the demo flat] → `walk-lighting`, `export-gltf`, `swatch-preview`, `plan-modes`, `render-on-demand` and `library-material` component tests run one by one through the heavy queue after the re-fetch; expected numbers may be re-measured, nothing in the lighting code changes.
7. [Bakes of scenes with those frames carry the old finish id] → they are refused by the shell check and made again.
